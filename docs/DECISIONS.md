# Decisions on points the spec leaves open

The spec (`PHASE1_SPEC.md`) is the source of truth. Where it is silent, incomplete or internally inconsistent, the defaults below apply
so that two developers and two Claude Code sessions do not invent different answers. Change a decision only by editing this file in a PR that both approve.

## Spec gaps found (schema is missing things the features need)

| ID | Gap | Decision |
|---|---|---|
| D-01 | Spec 7.1 asks for workspace "colour or icon", but table `workspaces` only has `icon`. | Add `colour` (VARCHAR, nullable) to `workspaces` in the initial migration. |
| D-02 | No table for email-verification tokens (spec 5.6) or pending email change (spec 6.2). | Add `email_verification_tokens` (same shape as `password_reset_tokens`, plus `purpose`: `verify_email` / `change_email`, and `new_email` nullable). Add `users.email_verified_at` (nullable timestamp) alongside `is_verified`. |
| D-03 | Users have no terms/consent record (spec 5.1 acknowledgement, 6.2 "manage consent"). | Add `users.terms_accepted_at` (timestamp) and `users.terms_version` (varchar). Registration is rejected without acknowledgement. |
| D-05 | Session list UI (spec 6.2) needs device info but `sessions` has none. | Add to `sessions`: `user_agent` (varchar, truncated), `ip_address` (inet or varchar), `revoked_at` (nullable), `remember_me` (bool). |
| D-06 | Theme and learning preferences (spec 6.2) have no storage. | Add table `user_preferences` (user_id unique FK, `theme` enum light/dark/system default system, `explanation_style`, `academic_level`, `study_preferences` JSONB). Reserved fields only; no logic. |
| D-07 | `users.status` values. | `pending_verification`, `active`, `suspended`, `deactivated`, plus `deletion_requested`. Use a CHECK constraint / enum. |
| D-08 | Activity log needs a readable description for the feed. | Add `activity_logs.entity_name` (varchar snapshot) and `workspace_id` (nullable FK, SET NULL) so the feed survives renames/deletes and can be filtered. Never store content beyond the name. |
| D-09 | Chapter `folder_id` must belong to the same subject (spec 12.3). | Enforce in the database with a composite FK `(folder_id, subject_id) -> folders(id, subject_id)` (add unique `(id, subject_id)` on folders) **and** in the service layer. |
| D-10 | `archived_at` exists on workspaces/subjects/folders/chapters but there is no `deleted_at`. | Delete = hard delete with explicit cascade rules (D-12). Archive = set `archived_at`. No soft-delete column in Phase 1 (spec 7.2 allows archive-then-delete). Add `deleted_at`-style soft deletion only if both developers agree. |
| D-11 | Unique names. | Unique (case-insensitive) per scope among non-archived rows: workspace name per user; subject name per workspace; folder name per parent; chapter title is not unique. Return 409 `CONFLICT`. |

## Behaviour decisions

| ID | Topic | Decision |
|---|---|---|
| D-04 | CSRF | Double-submit token: backend sets a non-HTTP-only `csrf_token` cookie; frontend echoes it in the `X-CSRF-Token` header on POST/PUT/PATCH/DELETE; backend compares with constant-time check **and** validates `Origin`/`Referer` against the allowlist. `SameSite=Lax`. |
| D-12 | Delete cascade | Deleting a workspace deletes its subjects, folders, chapters (DB `ON DELETE CASCADE`). Deleting a subject deletes its folders/chapters. Deleting a folder: **refused with 409 if it contains child folders or chapters**, unless `?cascade=true`, in which case contents are deleted. UI always shows a confirmation dialog stating what will be deleted. Archiving a parent hides children in lists but does not modify them. |
| D-13 | Default workspace | Registration creates a default workspace named "Personal" (type `personal_learning`). Exactly one default per user (partial unique index). The default workspace cannot be deleted until another is made default. |
| D-14 | Folder depth | Max depth 3 levels. Moves validated against self/descendant cycles and depth. |
| D-15 | Display order | Integer, gap-free per parent after reorder. `/chapters/reorder` accepts the full ordered id list for one subject/folder and runs in one transaction. |
| D-16 | Email verification policy | Unverified users can log in and use the academic features, see a persistent verification banner, and **cannot** change email, change password via settings, export data or request deletion until verified. |
| D-17 | Email delivery | Provider-agnostic `EmailSender` interface. Dev: Mailpit container in docker-compose (SMTP on 1025, UI on 8025). Console fallback. Real provider chosen later via `EMAIL_PROVIDER` env. Tests use an in-memory sender. |
| D-18 | Rate limiting | No Redis in Phase 1: use a small in-process limiter behind an interface (`RateLimiter`) so it can swap to Redis later. Limit per IP and per account/email for register, login, forgot-password, resend-verification, and resource creation. Return 429 with `Retry-After`. Document that multi-instance deployment needs the Redis backend. **Superseded in Phase 3 by D-63 and D-65 (Redis backend).** |
| D-19 | Session lifetime | Default session 7 days idle-sliding, absolute max 30 days; "remember me" extends idle to 30 days. Rotate session id on login and on password change. Changing password or resetting it revokes all other sessions. Cookie name `aw_session`, HTTP-only, `Secure` in production, `SameSite=Lax`, `Path=/`. |
| D-20 | Tokens | Session id, reset and verification tokens: 32 bytes from `secrets.token_urlsafe`, stored as SHA-256 hash. Reset token TTL 30 min; verification TTL 24 h; single use. |
| D-21 | Passwords | Min 12 chars, max 128. No composition rules. Check against a compromised-password list: use a local bundled list of the most common passwords (no external API call in Phase 1). Argon2id via `argon2-cffi`; benchmark parameters and record them in `docs/`. |
| D-22 | Re-authentication | Change password, change email, delete account, export data require the current password in the request (or a fresh login within 5 minutes). |
| D-23 | Account deletion | `DELETE /users/me` requires password + typed confirmation. Marks `deletion_requested`, revokes all sessions, then a deletion job (simple function invoked synchronously in Phase 1) deletes the user and all owned data (cascade), tokens, sessions, activity logs, and writes a content-free audit line (user id hash + timestamp). Settings UI explains exactly what is deleted before the final button. |
| D-24 | Data export | Add `GET /users/me/export` returning a JSON download of profile, preferences, workspaces, subjects, folders, chapters, activity. Requires re-auth (D-22). |
| D-25 | Security audit events | Structured JSON log on a dedicated `security` logger with correlation id, event type, user id (no PII beyond that), IP. Not stored in `activity_logs`. A DB audit table is a later option. |
| D-26 | Sidebar items | Real in Phase 1: Overview, My Workspace, Subjects, Recent activity, Archived items, Settings, Help and support (static help page), profile, logout. **Disabled "Coming soon"**: AI Tutor, Research Studio, Assessments, Revision, **Library**, **Favourites** (no storage in Phase 1 schema). |
| D-27 | Notifications icon | Visible placeholder with a disabled/“No notifications yet” popover. No fake notifications. |
| D-28 | Search/sort | Subjects: search by name, filter by workspace, sort by `name` or `updated_at`. Chapters: search by title within subject. Sort fields allowlisted. Case-insensitive `ILIKE` with escaped wildcards. |
| D-29 | Pagination | `limit` (default 20, max 100) and `offset`; list responses include `total`. |
| D-30 | Dashboard stats | Only counts computed from real rows scoped to the user. Empty states when zero. |
| D-31 | Security headers / CSP | Backend: `X-Content-Type-Options`, `Referrer-Policy`, `Cache-Control: no-store` on authenticated responses. Frontend (Next.js headers): CSP, `X-Frame-Options: DENY`/`frame-ancestors 'none'`, `Permissions-Policy`. HSTS in production. |
| D-32 | Row-Level Security | Not enabled in Phase 1 (application-level checks mandatory and tested). Evaluation of RLS is a documented follow-up in `docs/`. |
| D-33 | Database roles | Docker Compose creates an owner/migration role and a restricted application role without superuser. The app connects with the restricted role. |
| D-34 | Python/Node versions | Python 3.12, Node 22 LTS, PostgreSQL 16. Pin in Dockerfiles, `.python-version` / `.nvmrc`. Use `psycopg` v3 (matches `postgresql+psycopg://`). |
| D-35 | Language of UI | English only in Phase 1; `preferred_language` stored but not used for translation. |
| D-36 | Branding/UI | shadcn/ui default neutral theme, one accent colour, light/dark/system via CSS variables. Minimal, accessible, visible focus rings. |

## Phase 2 decisions (AI foundation)

Source: `PHASE2_SPEC.md`. Design: `AI_ARCHITECTURE.md`. Review of Phase 1: `AI_INTEGRATION_PLAN.md`. Entries marked **Adapted** differ from the proposed default; the reason is given.

| ID | Topic | Decision |
|---|---|---|
| D-37 | Model registry | The registry lives in code and config and is upserted into `llm_providers` / `llm_models` at startup, so usage records can reference them. No secrets in DB rows. **Adapted:** provider model ids are not literals in code (D-38); `LLM_DEFAULT_MODEL` becomes internal id `default`, and optional `LLM_ALLOWED_MODELS` adds more. Capabilities come from a profile declared in each adapter. |
| D-38 | Model ids | Never hardcode model IDs from memory. `LLM_DEFAULT_MODEL` comes from env. `backend/scripts/list_llm_models.py` (run in the container) lists the models the configured key can use and prints names, supported methods and token limits only, never the key. The chosen id and the date it was verified are recorded in `docs/LLM_PROVIDER_INTEGRATION.md`. **Chosen id: `gemini-3.5-flash-lite` (verified on: 2026-11-06)** via `list_llm_models.py` (it lists `generateContent` and `countTokens`), then a real streamed request (smoke test `--stream`: 2 chunks, provider-reported usage) and the opt-in live test through the SSE endpoint. `gemini-2.5-flash` is listed but returned 404 on the call; `gemini-3.8-flash` timed out on a streamed call and was not investigated further. **Pricing is still unverified (D-39), so cost stays NULL.** |
| D-39 | Pricing | A pricing registry holds input and output price per 1M tokens, currency and `effective_from`, filled only after checking the provider's current pricing page. Unknown price means cost is NULL, not 0. Each usage record stores a `pricing_version` snapshot so history is never recalculated. **Prices: pending verification.** |
| D-40 | Usage source | `usage_source` is `provider_reported`, `estimated` or `unavailable`; token fields are nullable. Thought/reasoning tokens, when reported, are part of `output_tokens` and also stored in `reasoning_tokens` (documented). A cancelled stream with no reported usage is `unavailable`, not a guess. |
| D-41 | System prompt | The system prompt is not a message row. Each assistant message stores `prompt_key` and `prompt_version`. Prompts live in versioned source files and are synced to `prompt_templates`; changing content means a new version. **Adapted:** adds `prompt_key` beside the spec's `prompt_version`. |
| D-42 | Ordering and regenerate | UNIQUE (`conversation_id`, `sequence_number`), assigned in a transaction that locks the conversation row. Regenerate inserts a new assistant row with `regenerates_message_id`; the old one gets `superseded_at`; context ignores superseded rows. **Adapted:** "superseded" is a nullable timestamp, not a status, so spec 9.3's statuses stay truthful (a regenerated answer is still "completed"). |
| D-43 | Concurrency and quotas | One active generation per conversation, enforced by a partial unique index on assistant messages in `pending`/`streaming`. Per-user cap on active generations (default 2) and per-user daily message and token quotas (conservative defaults, config). 429 with `Retry-After`. **Adapted:** the unique index cannot express a per-user cap, so that cap is enforced in the same transaction as the pending insert by locking the user row and counting; daily quotas are read from the database so they survive restarts and workers. |
| D-44 | Streaming | fetch-based SSE over POST (`EventSource` cannot POST), with credentials and `X-CSRF-Token`. Heartbeat comment every 15 s, `Cache-Control: no-store`, `X-Accel-Buffering: no`. Events as in Phase 2 spec 12.3, JSON-encoded. Partial content is flushed to the DB periodically and finalised on completion. Client disconnect cancels the upstream call and marks the message `cancelled`. |
| D-45 | Cancellation | In-process registry plus an explicit cancel endpoint. Single-instance limitation documented (same as D-18). |
| D-46 | Stuck generations | Messages in `pending`/`streaming` past `AI_STALE_GENERATION_SECONDS` are marked `failed` on startup and by a periodic check (every 60 s). |
| D-47 | Context policy v1 | Budget = model max input minus reserved output. Always include the system prompt and the latest user message; add recent complete turns newest to oldest until the budget is used. If the latest message alone is too long: 422 `LLM_CONTEXT_TOO_LONG`. Use provider token counting when the model has it, otherwise a conservative character estimate flagged as an estimate. |
| D-48 | Limits | In config: max input characters per message (default 8000), max output tokens (2000), history limit (20 messages), timeouts for connect, generation, stream inactivity and overall. |
| D-49 | Error codes | `LLM_NOT_CONFIGURED` 503, `LLM_AUTH_FAILED` 502 (generic user message), `LLM_RATE_LIMITED` 429, `LLM_TIMEOUT` 504, `LLM_UNAVAILABLE` 503, `LLM_CONTEXT_TOO_LONG` 422, `LLM_CONTENT_BLOCKED` 422, `LLM_INVALID_MODEL` 422, `LLM_BAD_RESPONSE` 502, `AI_QUOTA_EXCEEDED` 429, `AI_GENERATION_IN_PROGRESS` 409, `CONVERSATION_NOT_FOUND` 404. Errors after streaming has started are delivered as a `message.failed` event. **Adapted:** the status mapping is added here because the spec lists classes (14.7) but not per-code values. |
| D-50 | Retries | Only for transient errors and only before the first streamed token; maximum 2, exponential backoff with jitter, honouring `Retry-After`. Never retry after content has started. Retries are done by the orchestrator, not inside adapters. |
| D-51 | Logging | Never log message content, prompts or raw provider responses. Log ids, model, token counts, durations, error codes and the provider request id. |
| D-52 | Frontend rendering | `react-markdown` + `remark-gfm` + `rehype-sanitize`, no raw HTML, no `dangerouslySetInnerHTML`, safe links only (`http`, `https`, `mailto`, `rel="noopener noreferrer"`), code highlighting; math only if it works under the existing CSP. |
| D-53 | Deletion and export | Account deletion removes conversations, messages, feedback and usage records by FK cascade, and `/users/me/export` includes them. Deleting a conversation hard-deletes its messages and feedback; its usage records remain with `conversation_id` and `message_id` set to NULL until the account is deleted. **Adapted:** the SET NULL uses the PostgreSQL 15+ column-list form `ON DELETE SET NULL (conversation_id)` on a composite FK so `user_id` is not nulled; M1 verifies that SQLAlchemy and Alembic emit it, with a service-level fallback if not. |
| D-54 | Privacy notice | First-use notice in the AI Tutor that conversations are sent to Google's Gemini API; acknowledgement stored in `user_preferences.ai_notice_acknowledged_at` (migration). The text names the provider from configuration, not hardcoded in the component. **Implemented (M4):** `GET /ai/status` supplies `provider_display_name`, `is_test_provider` and the input limit; `POST /users/me/ai-notice/acknowledge` stores the first acknowledgement time (idempotent); the UI blocks the tutor until it is acknowledged. |
| D-55 | Titles | Deterministic from the first message: first ~60 characters, whitespace collapsed; the user can rename. No LLM call. |
| D-56 | Scoping | All AI queries are scoped by `user_id`; non-owned resources return 404. Composite foreign keys keep messages, usage and feedback from pointing at a conversation with a different owner (Phase 2 spec 13.3). |
| D-57 | Gemini adapter | System prompt via the SDK's system-instruction field; our `assistant` role maps to Gemini's `model` role; blocked/safety finish reasons map to `LLM_CONTENT_BLOCKED`, max-tokens to a completed message with `finish_reason = length`; usage from the response usage metadata; thinking budget limited or disabled where the model supports it. SDK surface verified against the pinned version in M1. |
| D-58 | No provider | The app runs normally with no provider configured: AI endpoints return 503 `LLM_NOT_CONFIGURED` and the AI Tutor shows a clear message. |
| D-59 | Sidebar (amends D-26) | The AI Tutor sidebar item is enabled in Phase 2. Research Studio, Assessments, Revision, Library and Favourites stay disabled "Coming soon". The Vitest assertion and the Help page text change in the same PR as the page. |
| D-60 | FakeProvider | For automated tests and local UI development only. Allowed only when `APP_ENV` is `development` or `testing` and `LLM_PROVIDER=fake` is set explicitly; it refuses to start in `production` (and any other environment), and `Settings` rejects it in production as a second check. When active, the API reports `provider_kind: "test"` and the UI shows a permanent "Test provider, not a real AI" badge. Reconciles the spec's "no fake AI output" (section 26) with the need for deterministic tests. |
| D-61 | Constraints and migrations | Every constraint (partial unique indexes, composite FKs, CHECKs) is declared on the SQLAlchemy model, because tests build the schema with `create_all`. CI compares the migrated schema with the model metadata. New tables are granted to `axonweave_app`, verified by a test that connects as that role (tests otherwise use the owner role). |

## Phase 3 decisions (Document Intelligence and RAG)

Source: `PHASE3_SPEC.md`. Review: `DOCUMENT_INTELLIGENCE_PLAN.md`. Design: `DOCUMENT_ARCHITECTURE.md`. Entries marked **Adapted** differ from the proposed default; the reason is given.
Facts that change quickly (image tags, model ids, emulator status) are **verified in M1/M4 and recorded here with the date**, not copied from memory.

| ID | Topic | Decision |
|---|---|---|
| D-62 | pgvector | Local dev and CI use a pgvector-enabled PostgreSQL 16 image (`pgvector/pgvector`, tag pinned in M1; D-34 keeps major version 16). `CREATE EXTENSION IF NOT EXISTS vector` runs in an Alembic migration as the owner role (D-33); the app role gets `USAGE` on the schema and the usual table grants, never superuser. The Python `pgvector` package registers the type in the app and in `alembic/env.py`. **Verified 2026-11-06 (M1):** image `pgvector/pgvector:0.8.7-pg16` (PostgreSQL 16.15, pgvector extension 0.8.7), used in compose and CI; Python package `pgvector==0.5.1`. The filtered-ANN behaviour is still to be measured (see D-73). The init scripts keep working because that image is Debian-based, not Alpine. |
| D-63 | Redis, Celery, object store (amends D-18 and the "no Redis" rule) | Compose adds `redis`, `worker` (Celery), `beat` (Celery beat) and an S3-compatible emulator. **Emulator: SeaweedFS** (Apache-2.0, actively maintained, S3 API). MinIO Community Edition is reported archived upstream in 2026 (sources differ on the exact date), so it is not used for new work; Garage (AGPL, needs a config file) and RustFS (young, release-candidate versions) are the recorded alternatives. The choice is isolated behind `StorageBackend` and a few env vars, so swapping is configuration. **Pinned 2026-11-06 (M1):** `chrislusf/seaweedfs:4.50`, S3 enabled with one identity taken from `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`; verified with the S3 contract tests, including a 3-part multipart upload. Upstream MinIO status was not re-checked beyond the research recorded here. `CLAUDE.md`, `README.md` and D-18 are updated. Phase 1 and 2 features must still start and pass tests when Redis, worker and store are not running (only document endpoints answer 503). **Adapted:** the default says "choose after checking"; the check is recorded here and repeated at pin time. |
| D-64 | Storage and downloads | `StorageBackend` interface with S3 and in-memory implementations (the in-memory one refuses production). Keys are generated by the backend only (`users/{user_id}/documents/{document_id}/v{n}/original.{ext}`, extension from the validated type), never from user input; bucket private; server-side encryption where the store supports it. Downloads are **streamed by the backend** after the full ownership check (`Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`); no public URLs; presigned URLs are off by default and, if ever enabled, are short-lived and issued only after the same check. Non-owned documents: 404. Only originals go to object storage; extracted text lives in the database. |
| D-65 | Rate limiter on Redis (supersedes D-18's in-process backend) | A `RedisRateLimiter` implements the existing `RateLimiter` protocol (sliding window, one atomic script per key). The in-process limiter stays for tests and for development without Redis. **Adapted:** when Redis is unreachable the limiter neither fails open nor rejects all traffic; it falls back to the in-process limiter for that process, logs a security event and recovers automatically. Failing closed would make login and the whole app depend on Redis; failing open removes brute-force protection. Fallback limits are per instance, the same as Phase 2 behaviour. |
| D-66 | Deletion and export | Documents are **hard-deleted**; the DB cascades to versions, chunks and jobs. Storage objects are removed through a `storage_cleanup` outbox table (no FK to users) written in the same transaction as the delete and processed by a Celery task with retries, so the DB and storage never diverge silently; a periodic reconciliation finds objects with no document row. Every path that can cascade to documents (document, folder, chapter, subject, workspace, account) goes through one service function that writes outbox rows first. On document deletion, `message_citations` keep only the document name and page/slide: `chunk_id` and `document_id` become NULL, `available=false`, `snippet` is cleared. **Adapted:** `section_heading` is also cleared, because a heading can carry document content. Account deletion (D-23) deletes all documents and objects; export (D-24) includes document **metadata only** (no file bytes, no extracted text) and the citations of the user's own messages (names and pages). |
| D-67 | Schema fixes to the spec | `document_chunks` gets `user_id` with composite FK `(document_id, user_id) -> documents(id, user_id)`; a generated `tsvector` column with a GIN index; optional `bboxes` JSONB (PDF block coordinates for citation highlighting); `embedding_model`, `embedding_dimensions`, `index_version`. New `message_citations` table (message, rank, nullable chunk and document, document_name, document_version, page, slide, section_heading, snippet, score, available). `conversations.scope_type`/`scope_id` with a CHECK and service-level ownership validation; each message records the scope and answer mode used. `ai_usage_records.request_kind` (`chat`/`embedding`/`generation`). Documents carry `workspace_id` plus optional subject, folder, chapter with composite FKs so the chain is consistent in the database; no `deleted_at` (D-10 stands); chunks reference `document_version_id`. All constraints on the models (D-61). |
| D-68 | Status, versions, idempotency | The version's `processing_status` is authoritative; the job `stage` drives progress; `documents.processing_status` is a denormalised copy of the latest version. Only the `active_version` of a document whose version is `completed` is searchable; switching `active_version` is one transaction. Idempotency: `UNIQUE (document_version_id, chunk_index)`; every run has a `pipeline_version` and a job id; a rerun deletes and rebuilds that version's chunks inside one transaction; a **partial unique index** allows one `running` job per version; embedding happens before the write transaction. Statuses use the spec names. |
| D-69 | Embeddings | `EmbeddingProvider` interface mirrors `LLMProvider` (own error taxonomy, no retries in adapters, honest usage, timeouts). Gemini adapter first (existing key, own settings class); a local sentence-transformers adapter is possible later (one file + one registry line); `FakeEmbeddingProvider` is deterministic, only for development/testing with explicit opt-in, refuses production, `Settings` rejects it in production, and the API reports `embedding_kind: "test"`. The model id is **never hardcoded from memory**: `backend/scripts/list_embedding_models.py` lists what the key can use, and the chosen id, its dimension and the verification date are recorded here: **`gemini-embedding-001`, 768 dimensions (`output_dimensionality`, vectors L2-normalised), verified 2026-11-09** (see `docs/RETRIEVAL_EVALUATION.md`). The dimension lives in config and in the column definition (768, verified, in `app/database/vector.py`, used by the model, the migration and a startup check that rejects a different `EMBEDDING_DIMENSIONS`; verified against the chosen model); embeddings from different models or dimensions are never mixed in one index; changing the model builds a new `index_version` and switches the active index when it is complete. Embedding calls write `ai_usage_records` (`request_kind = embedding`) and count against the token quota; unknown price is NULL (D-39). Document text is sent to the embedding provider, so the privacy notice (D-54) is extended before upload is enabled. |
| D-70 | Worker isolation | Extraction and OCR run only in the Celery worker (its own image target with OCR binaries; the API image has none and never imports parser libraries). Per-job soft and hard timeouts, caps on pages, extracted characters and OCR DPI, a container memory limit, non-root user, read-only root with a tmpfs scratch directory, temp files removed in `finally`. The worker network is restricted to Redis, Postgres, the object store and the embedding provider. Links in documents are never followed and macros are never executed. |
| D-71 | Upload security | Size limit enforced **while streaming** (413, never buffer a whole file); magic bytes validated, browser MIME ignored; display names sanitised (control characters, path separators, length, Unicode normalisation); quotas for files per request, documents per user and bytes per user (configurable, counted in the database); docx/pptx zip checks (entry count, total uncompressed size and ratio, no nested archives, no path traversal in entry names); image decompression-bomb limit (pixel count); optional ClamAV behind a `Scanner` interface, **off by default and fail-closed when enabled** (scanner down = upload refused with 503). No legacy `.doc`/`.ppt`. |
| D-72 | Viewer | PDFs are rendered with pdf.js in the browser from bytes fetched from a separate **inline** endpoint, which returns `Content-Type: application/pdf`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`, and requires the same ownership check; no iframe is used. The frontend CSP gains only `worker-src 'self' blob:`. PPTX and DOCX show extracted text by slide/section (no rendering); text and markdown show extracted text; images use the same inline endpoint with their detected type. Uploaded HTML is rejected at upload and never served. The no-store cache rule is extended to `library`, `documents` and `ai-tutor`. |
| D-73 | Retrieval | Measure first. Baseline is **exact filtered search** (user + verified document ids + active version + current index). An ANN (HNSW) index is added only if measurement shows it is needed, and recall is tested with the filters actually used. M1 checks the installed pgvector version and tests `hnsw.iterative_scan` behaviour for filtered queries (the pgvector 0.8.0 release notes introduce iterative scans; the installed version is what counts). Hybrid = vector top-k plus full-text top-k fused with Reciprocal Rank Fusion. No reranker yet. Minimum-evidence threshold, top-k and context token budget are configurable. One `POST /search` endpoint with `mode` replaces the three spec endpoints (plan, conflict 10). |
| D-74 | Cancellation registry | The chat `GenerationRegistry` stays in the API process (D-45 stands; single-instance limit documented). Ingestion jobs are cancelled with a DB cancel flag checked between stages plus Celery revoke, not through this registry. Stale jobs are failed by a periodic sweeper (like D-46). |
| D-75 | RAG | Answer modes `document_only` / `document_first` / `general`. In `document_only`, if no chunk passes the threshold, the backend returns a fixed insufficient-evidence reply **without calling the LLM**. Reference material is wrapped in unambiguous markers; marker-like text inside document text is escaped; the prompt states the material is untrusted data and cannot change instructions. Sources are numbered `[1]..[n]` per answer; the backend strips markers that do not map to a retrieved chunk and takes page/slide/title from the database, never from model text. Streaming: `message.citations` (the retrieved sources) is sent before the first delta; `message.completed` carries the validated final text and citations, and the client replaces the streamed text if different. Follow-ups: v1 builds the retrieval query from the current question plus the previous user question when the current one is short; an LLM rewrite is a later option behind a flag. Scope is stored on the conversation, not trusted per request; prompts are versioned (`rag_*` keys, D-41). |
| D-76 | Test data | No copyrighted material in git. Fixtures (PDF, PPTX, DOCX, scanned-style PDF, hostile files) are generated in code. Real test documents live in `testdata-private/`, which is added to `.gitignore`. Evaluation reports record counts and metrics, never document text. |

| D-77 | Worker egress and malware scan (M7 follow-up) | The worker keeps `internal: true` (no direct route) and reaches only the embedding provider through an allow-listed Squid `egress-proxy` (HTTPS CONNECT to `generativelanguage.googleapis.com`, deny all else); `GEMINI_API_KEY` is passed to the worker. Malware scanning: `SCANNER_BACKEND=clamav` uses a clamd INSTREAM adapter, fail closed (unreachable or unreadable reply gives 503, infected gives 422 `MALWARE_DETECTED`); optional compose profile `scan`. |

## Phase 4 decisions (AI-Powered Study Generation)

Source: `PHASE4_SPEC.md`. Design: `STUDY_GENERATION_ARCHITECTURE.md`. Written in M0; later milestones add entries.

| ID | Topic | Decision |
|---|---|---|
| D-78 | Engine shape | One generation engine in `backend/app/study/` (request schema, generator registry, `SourceReader`, prompting, validation, engine) and routes/service in `app/modules/study/`. A generator declares settings model, output model, prompt key, source mode and semantic checks; it never reads sources, calls the provider, saves, queues or tracks usage itself. Phase 3 pipelines (extraction, chunking, embeddings, retrieval, citations) are reused, not rebuilt. |
| D-79 | SourceReader | One interface, three read modes over a `ScopeResolver`-verified document set (completed active versions only; foreign or missing ids are 404): **ordered** (all chunks in reading order, refuses with `GENERATION_SOURCE_TOO_LARGE` rather than cutting silently), **sampled** (evenly spaced chunks across the scope within the token budget, reports `truncated`), **retrieved** (Phase 3 hybrid `Searcher` for a query). `ordered_batches` splits the whole scope into consecutive batches so map-reduce (M1) can prove every chunk reached the reducer. A generator chooses its mode and whether a too-large ordered scope falls back to sampling. Source kinds: document, documents (max 20), chapter, subject, folder, workspace, pasted text. A chunk-collection source is deferred. |
| D-80 | Prompts and structured output | System prompts live in the existing prompt registry (`study_*` keys, versioned, immutable once released; common rules plus one prompt per generator). Source text goes in the user turn inside escaped SOURCE markers and is untrusted data. One structured-output path: provider-native structured output when the model supports it, else a JSON-only instruction; the Pydantic output model is the validation boundary (required fields, types, array lengths, difficulty values, source references, duplicates). Invalid output gets **exactly one** correction call (the request lists field paths and rule names only, never values); a second failure fails the job with `GENERATION_INVALID_OUTPUT`. Source references the model invents are stripped, as with Phase 3 citations. |
| D-81 | Providers and models | Model chosen through the existing registry (`STUDY_GENERATION_MODEL` internal id, else the default); the input budget is the smaller of `STUDY_MAX_INPUT_TOKENS` and 80 percent of the model's verified input limit; output tokens are capped by the generator, `STUDY_MAX_OUTPUT_TOKENS` and the model. No model id or price is hardcoded (D-38, D-39). The worker needs the LLM environment (compose `x-llm-env`); the Gemini host is already in the worker egress allow-list (D-77). |
| D-82 | No duplicated source content | A study material stores the structured result plus source *references* (rank, document id, chunk id, page, slide), never source text. A pasted-text source is held in the job request only until read, then removed (also on cancel or failure). Job and material responses never contain source text, prompts or provider errors. Answer keys (M3) are stored once, in the quiz tables, and no question endpoint returns them before submission. |
| D-83 | Versions and edits | `study_material_versions` holds immutable snapshots; version 1 is the original generated content (`origin=generated`, `created_by` NULL). Edits and restores add versions. Regeneration (M5) is a preview/proposal and never overwrites user edits. Subject and chapter links are cleared (`ON DELETE SET NULL (column)`) when those are deleted; deleting a workspace or user cascades. |
| D-84 | Jobs and statuses | `generation_jobs.id` is the generation id. Statuses: pending, retrieving_sources, generating, validating, saving, completed, failed, cancelled. Progress 0 to 100, heartbeat, safe `error_code` only (user text comes from a fixed code-to-message table). Runs in Celery (`study.run_generation`, own time limits); the API only enqueues. No provider call from the API process. |
| D-85 | Reliability | The worker claims a job with an atomic `pending -> retrieving_sources` update, so a redelivered or duplicate message does nothing. No automatic Celery retry. Provider errors that prove nothing was processed (busy, unavailable) are retried up to `STUDY_PROVIDER_MAX_RETRIES`; a timeout is never retried (the provider may have run and billed). A worker that dies mid-run leaves the job to `study.sweep_stale_jobs`, which fails it (`GENERATION_INTERRUPTED`) instead of restarting an expensive generation of unknown outcome. `study.dispatch_pending` re-sends jobs that were committed but never delivered. |
| D-86 | Cancellation | A pending job is cancelled at once; a running job gets `cancel_requested`, which the engine checks between stages and every `STUDY_CANCEL_POLL_SECONDS` while the provider call is in flight (the call is cancelled and logged as a `cancelled` usage row). A finished job answers 409 `GENERATION_NOT_CANCELLABLE`. Nothing is saved after a cancel. |
| D-87 | Duplicate prevention | Each request gets a fingerprint (user, generator, canonical source, validated settings with defaults filled in). A partial unique index allows one *active* job per fingerprint; an identical request returns the active job (200, `existing: true`) instead of starting another. A finished job does not block a new request. |
| D-88 | Limits, quotas, usage | Per user: requests per minute, daily generation jobs (jobs that never reached the provider do not count), simultaneous active jobs, plus the existing daily token quota (generation usage counts toward it). Per request: max documents, max pasted text, max scope tokens, max input and output tokens, per-generator max items, job timeout. Every provider attempt writes an `ai_usage_records` row with `request_kind='generation'` (unknown tokens and cost stay NULL). Logs carry ids, counts, codes and durations only. |
| D-89 | Preferences | User generation preferences (spec 16) live in their own table `study_generation_preferences` (language, explanation level, summary length, question difficulty, include examples/definitions/references), user-set values only, nothing inferred. M0 creates the table; endpoints and use as defaults arrive in M5. |
| D-90 | Echo generator | `echo` is a test-only generator that proves the engine end to end. It is invisible and refused when `APP_ENV=production`. Real generators (M1 onward) register in `app/study/generators/registry.py`. |
| D-91 | Map-reduce for long scopes | A generator with `map_reduce = True` (the summary) reads a scope that exceeds the input budget as ordered batches (at most 30). Each batch is condensed into notes by one call (source numbers stay global); the notes of ALL batches go to one reducer call, after at most 3 condense rounds if they would not fit, else `GENERATION_SOURCE_TOO_LARGE`. The material stores a `coverage` report (documents, chunks included, batches, complete). Nothing is silently skipped; sampling is never used for summaries. Intermediate notes are never stored. |
| D-92 | Edit, versions, regenerate | Edits (`PATCH /study/materials/{id}`, with `expected_version`), restores and applied regenerations each create a new version; version 1 (original) is never changed. A mismatch is 409 `MATERIAL_VERSION_CONFLICT`. Regeneration (whole or one section) is a generation job whose result is stored as `generation_jobs.preview` and touches nothing until `POST /study/generations/{id}/preview/apply`; a preview made against an older version is 409 `PREVIEW_STALE`, so later edits are never overwritten. A section preview's references are re-mapped onto the material's own source list by chunk id. Summaries from pasted text cannot be regenerated (text is not stored, D-82). The `regenerate` request field is internal and rejected from clients. |
| D-93 | Flashcards | A deck is a `flashcard_sets` row (one per flashcard material) plus `flashcards` rows (spec 18.4, 18.5); the cards are the live, editable state and the material keeps the original generated snapshot as version 1. Because of that the generic material edit, restore and regenerate paths refuse decks (422); cards are edited through `/study/flashcards/*`. Quality rules (one concept, front 5 to 400 chars, back at most 1200, fill-in-the-blank needs a `___` blank and a short answer, front and back not identical) apply to generated and typed cards. A generated card whose source numbers do not map to a real source is dropped (unsupported); word-set similarity of 0.8 or more between cards is a near-duplicate, which fails validation (one correction call) when generated and is refused (409 `FLASHCARD_DUPLICATE`) when typed. Each card has a `revision` that counts content edits. Regenerating selected cards is a preview job; applying it replaces the selected cards in place and answers 409 `PREVIEW_STALE` if any of them was edited or deleted meanwhile, and keeps the user's card where the replacement duplicates another card. |
