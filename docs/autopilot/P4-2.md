# P4-2 - Phase 4 M2: Flashcard generator

## What was built
Backend only.
- **Tables** (migration `0006`, one head): `flashcard_sets` (one per flashcard material) and `flashcards` (front, back, explanation, card type, difficulty, `source_references` JSONB, display order, favourite, origin, `revision`). Composite owner foreign keys, explicit grants.
- **Generator** `flashcards` on the M0 engine and registry, prompt `study_flashcards` v1. All six card types (basic, definition, concept, comparison, fill-in-the-blank, application). Settings: count (1 to 50), card type (or mixed), difficulty (or mixed), language, include examples, explanations and source references.
- **Quality rules**: front 5 to 400 characters, back at most 1200, front and back not identical, fill-in-the-blank needs a `___` blank and an answer of at most 120 characters, requested count/type/difficulty respected. Near-duplicate detection (word-set similarity of 0.8 or more) fails validation, so it gets the engine's single correction call. A card with no valid source number is dropped as unsupported.
- **Source reference per card**: source numbers are mapped to document id, chunk id, page and slide (ids and locations only, never text). Invented numbers are stripped.
- **Endpoints** (`/api/v1/study/flashcards`): `GET /{set_id}`, `POST /{set_id}/cards`, `PATCH /cards/{id}` (also favourite), `DELETE /cards/{id}`, `PUT /{set_id}/order`, `POST /{set_id}/regenerate` (a preview job), `POST /{set_id}/regenerate/{job_id}/apply`. The existing `GET /study/generations/{id}/preview` shows the preview.
- **Regenerate selected cards**: a preview that changes nothing until applied. Apply replaces the selected cards in place, and answers 409 `PREVIEW_STALE` if any selected card was edited or deleted since the preview, so user edits are never overwritten. A replacement that duplicates a kept card leaves the user's card as is.
- Generic material edit, restore, regenerate and preview-apply refuse decks (422/409); cards are edited card by card.
- Decision D-93, `docs/AUTOPILOT_LOG.md` entries, M2 ticked in `docs/TASKS_Phase4.md`.

## Decisions made (with reasons)
See D-93 and the P4-2 lines in `docs/AUTOPILOT_LOG.md`: own tables (per-card edit, reorder, favourite); the material keeps the version-1 snapshot; unsupported cards dropped rather than failing the job; similarity threshold 0.8; per-card `revision` for edit protection; `PUT .../order` with the full id list; caps 50 per generation, 200 per set, 30 per regenerate.

## NOT verified / limitations
- No real LLM was called (Fake provider only). Output quality, real-model compliance with the JSON shape and the 0.8 duplicate threshold on real text are untested.
- The default `STUDY_MAX_OUTPUT_TOKENS` is 4000, which may truncate a 40 to 50 card request on a real model; raise it if needed.
- Applying a regeneration is not row-locked: an edit committed in the same instant as an apply could be lost (a window of milliseconds). The `revision` check closes the normal case.
- Deleting a source document does not mark card references unavailable yet (M5).
- Frontend not touched (M6). API types not regenerated in this run.
